# Motion Showreel

把一個想法做成以圖形、文字或介面動畫為主的影片，交付 MP4 和能重建的原始碼。保留短片的動效密度和創意自由，也支援按章節製作最長 20 分鐘的內容。

**原理**：頁面暴露確定性的 `render(t)`，腳本逐幀截圖，再用 ffmpeg 合成 MP4。畫面、口播、配樂和音效共用 `timeline.js`。無口播時按內容和音樂節拍組織畫面；有口播時以真實語音時間為準，再安排音樂和音效。

**不需要顯示卡、不需要模型、不需要雲端 API**（只有要 TTS 旁白時才需要對應的 API 設定）。這是「用程式碼畫動畫」，不是擴散模型生成影片。

**語言與台灣預設配置**：與使用者對話、`brief.md`、畫面文案、字幕與配音預設一律使用**台灣繁體中文（`zh-TW`）與台灣口音／字型配置**，不要輸出簡體中文；字型優先使用 `fonts.mjs` 下載的台灣繁中字型（預設 `Noto Sans TC`）或 `PingFang TC` / `Microsoft JhengHei`；選用 AI TTS 且未指定其他服務時，預設使用免 API Key 的 Edge TTS 台灣口音（女聲 `zh-TW-HsiaoChenNeural`、男聲 `zh-TW-YunJheNeural`）。使用者明確指定其他語言、字型或口音時，依其指定，並在 brief 記下。

**預設先預覽，再匯出**：所有類型都先開啟剪輯工作區讓使用者檢視真實畫面與聲音。使用者點選「匯出影片」或在對話中確認預覽通過、可以匯出後，才合成 MP4。首次要求「做一個影片」不等於預覽已經通過；只有使用者明確免除預覽時才能直接匯出。靜幀、自查和音訊準備可提前進行，不預設生成代理 MP4 或整片樣片。

**按需觀看製作過程**：需求問答時識別「邊做邊看、即時進度、每個階段看看」等意願；使用者表達後就提前開啟進度頁，從需求說明到風格幀、口播樣例、鏡頭與混音逐步展示。按 `references/progress.md` 發布已自查的階段成果，不直接載入半成品程式碼。收到使用者確認後，先用 `progress.mjs <project> --stage <當前階段> --confirm --message "已確認，正在……"` 解除等待，再進行調研、下載或製作；不等產物做完才補進度。未提出時保持預設的最終工作區預覽；不改變製作標準、確認節點和成片驗收。

**好片子從哪來**：變化密度、運動質感、一個記憶點、音畫關係，這四項通常決定觀感。但具體怎麼動、動多少，由**風格和內容**決定，不是每支片子都要多機位、彈簧和滿屏音效。全域只守幾條底線（見「底線」），其餘都是給模型的起點，不是天花板。

**影片感**：講解、產品演示和敘事片要讓物件的行為與關係隨內容發展，保持鏡頭間的空間承接。不能把口播逐句變成靜態標題卡，再用淡入、縮放和背景粒子包裝。分鏡先寫清「觀眾要看懂什麼變化、主體前後狀態、如何接上一個鏡頭」，再選動效。Logo、動態排版、循環與刻意靜止的風格仍按自身語法製作；不靠持續亂動或強制 60fps 判定好壞。具體方法見 `references/craft.md` 的「連續敘事」。

## 適用範圍

| 使用者想要 | 用這個 Skill？ |
|---|---|
| 產品宣傳短片、動效作品集、UI 動效、動態排版／卡點、Logo 演繹、片頭、循環動圖 | ✅ |
| 影片模型生成的綠幕人物 + 程式碼做的場景、大字、動效 | ✅ 人物由使用者提供（`references/formats.md` H 類） |
| 使用者提供口播稿或錄音，要匯出有講解的 MP4 | ✅ 口播驅動模式；TTS 必須使用使用者提供的原稿 |
| 需要點選推進、現場演講、互動式網頁演示，或文章轉口播稿 | ❌ 本倉庫未收錄對應技能，需另行安裝 |
| 網頁、落地頁、互動原型、靜態視覺稿 | ❌ 不屬於本技能範圍 |
| 寫實人物表演、實拍質感、剪輯既有素材、用影片模型直接出畫面 | ❌ 改用 `ai-food-shorts`（圖生影走 Google Flow）或外部影片模型 |

**時長**：最長 20 分鐘（1200 秒），以使用者確認的時長為準。短片仍適合 5–60 秒，不把長片做成連續二十分鐘的高密度卡點。超過 2 分鐘，讀 `references/long-form.md`，按章節規劃、製作和審片。使用者指定時長與口播實際長度或內容量衝突時，停下來確認調整方案，不擅自截斷、加速口播或改變片長。

## 模型的長處和預設坑

- **長處**：一個檔案裡能混用 Canvas、SVG/DOM、WebGL、Three.js，甚至每段換一種媒介；運動可以用公式精確計算（閉式彈簧、節拍網格、子幀運動模糊）；聲音和畫面讀同一張時間表；能長時間自主「渲靜幀 → 看圖 → 修改」；審美判斷力強，一句「全力以赴」就可能出很驚豔的東西。
- **預設坑**：沒有約束時，畫面會落到深色背景、置中大字的淡入、紫藍漸變加發光、機位不動；配樂會落到 A 小調四踩、每個重拍 impact + crash、鐘聲落版，幾支片子聽起來像同一首歌。所以要先找對標（畫面和聲音都要）、寫清風格和禁止清單。但約束也不能寫死：這個 Skill 的風格庫和手法庫都是起點，主題需要時隨時改造、混搭或自訂。
- **做不好的**：寫實人物、複雜的手部／布料／毛髮、需要真實物理精度的東西、照片級產品（除非使用者提供模型或圖片）。遇到這些就風格化處理，或者換成綠幕人物 + 程式碼場景的分工。

## 工作流

```
0 環境檢查（一次）
1 需求確認 ──────── 補齊必填項，彙總要求 → 🛑 等使用者確認
2 brief.md ──────── 對標 → 用途 + 風格 → Reel Read → 分鏡 + 聲音計畫
3 風格幀 ────────── 已定風格：3 張幀；未定風格：3 個方向各 1 張 → 🛑 等使用者確認
4 製作 ──────────── 有口播先準備真實音訊及時間戳 → timeline → 逐鏡頭 → 網頁自查
5 配樂與混音 ────── BGM、音效獨立選來源；有口播時人聲優先
6 工作區預覽 ────── 主動開啟剪輯工作區，修改後複看 → 🛑 等使用者確認匯出
7 匯出與驗收 ────── 合成 MP4 → 技術檢查（必須全過）+ 成片複核
8 交付
```

工作目錄：在使用者目前目錄下建 `<slug>/`，所有檔案都放在裡面：`brief.md`、`index.html`、`motion.js`、`timeline.js`、`score.mjs` 或 `score.tone.js`（按 scaffold 的 `--audio` 選擇）、`build.sh`、`fonts/`、`assets/`、`audio/`、`qa/`、`out/`。

### 第 0 步：環境

第一次使用時執行 `sh <skill>/scripts/setup.sh`：它會安裝 Playwright 和 Chromium，再跑 `check-env.mjs`。需要 Node 18+ 和 ffmpeg；缺了就告訴使用者怎麼裝，不要替使用者裝系統軟體。工具自帶測試：`cd <skill>/scripts && npm test`。

### 第 1 步：需求確認（停下來等使用者）

集中補問缺失項，已經提供過的不重複問。以下資訊必須明確，不能用固定預設值代替使用者決定：

| 必填資訊 | 需要明確什麼 |
|---|---|
| 核心主題、製作內容 | 要呈現什麼，哪些內容必須出現 |
| 時長 | 明確秒數或分鐘數，是否允許小幅浮動；不得超過 1200 秒 |
| 橫屏或豎屏 | 按選擇確定實際尺寸；也保留使用者明確指定 1:1 等其他畫幅的能力。解析度、幀率可提出建議，並寫入確認摘要 |
| BGM 來源 | AI 自主合成／使用者提供；使用者的也可明確關閉 |
| 音效來源 | AI 自主合成／使用者提供；與 BGM 分開選擇，也可關閉 |
| 口播方式 | 無口播／AI TTS／使用者提供錄音 |

**條件必填**：選 TTS 時必須由使用者提供口播稿，不代寫、不補寫、不改寫後擅自合成；未指定 TTS 服務時預設使用免費、免 API Key 的 **Edge TTS 台灣口音**（`zh-TW-HsiaoChenNeural` / `zh-TW-YunJheNeural`，自動產出詞級時間戳），亦可指定 Gemini、MiniMax、OpenAI 或自訂適配器（憑證用環境變數，不寫進 brief），按需讀 `references/narration.md`。選使用者錄音時，需要錄音檔或可存取位址；選使用者 BGM／音效時，需要相應檔案。口播語言、音色等能從稿件或設定判斷的寫入摘要，否則一併詢問。

**可選資訊**：相關資料、受眾與發布平台、主題風格、語言與用語。受眾和平台未給時根據內容推斷，並在摘要說明。語言未給時預設台灣繁體中文，使用者要簡體、粵語或英文版時以其指定為準並記入 brief。風格未給時留到風格幀階段提供三個方向。

**製作進度偏好**：從使用者已有回饋判斷是否希望看過程，明確表達就記錄並啟用，不重複確認、不增加必答題。啟用時讀 `references/progress.md`，儘早啟動 `editor.mjs <slug> --progress` 並主動開啟；目錄可以暫時沒有動畫或音訊。在需求摘要中寫明會逐階段展示，後續仍等原有需求與風格確認。

**素材怎麼處理**：使用者已經給了具體內容並授權 AI 生成，就據此製作；使用者未給足具體內容時，詢問必要資料，也可以根據主題開展網上調研並保留來源。有口播稿時先從原稿提取資訊，不再讓使用者重複填寫。AI 可生成插畫、場景、抽象圖形和明確標註的示意內容；真實產品功能、數字和品牌素材仍守「底線」，不能用虛構資料冒充真實內容。品牌 Logo 或真實產品截圖的要求見 `references/stack.md`。

- 使用者給了參考影片：先跑 `inspect.mjs sheet <ref> --cells 30` 看全貌，`inspect.mjs grid <ref> --strips` 量出剪點和它們落的節拍網格（BPM 候選、每段佔幾步、每個轉場的連續幀），`inspect.mjs heat <ref>` 看每段裡哪裡在動、動多大面積。把量到的數寫進 brief 的對標一欄。只學結構和手法，不搬素材。
- 使用者給了曲子：無口播時先跑 `audio.mjs beats <track> --out <slug>/audio/beats.json`；有口播時音樂拍點服從講述節奏。
- 畫面裡要出現的產品、品牌或技術名詞，不確定的先查證。

補齊後彙總主題、時長、畫幅、BGM／音效各自來源、口播方式和素材情況，**停下來等使用者確認，再寫 brief**。即便首次請求資訊齊全，也先發摘要確認。使用者說「全力以赴」「給我驚喜」「你看著辦」只授權創意選擇，不代表可省略必填資訊或跳過確認；只有使用者明確要求跳過某次確認時才可繼續，記錄其授權。

**放手模式**：保留創意自主權，只守底線和技術管線，風格、結構、手法可自行判斷，也可完全不用風格庫。仍寫 brief、提供三個方向，完成需求與風格確認；製作後同樣先在工作區預覽，再確認匯出。使用者明確免除的確認除外。

### 第 2 步：brief.md

**先找對標**：動筆前為這支片子（這個主題 + 這種用途）挑 1–2 個對標作品，可以是電影片頭、廣告、遊戲、動效作品、設計流派。在 brief 裡寫下「學什麼」（構圖、節奏、鏡頭語法、配色邏輯、配樂結構）和「不學什麼」（角色、具體鏡頭、旋律、logo、字型檔）。對標比任何規則都更能拉高上限。

**再想三個候選結構**：比如一段旅程、一次前後對比、一次倒數、一個變成另一個、一個不切鏡頭的長鏡頭。各用兩三行寫下來，選一個並寫明理由。第一個冒出來的想法往往是這個風格的陳詞濫調。

**用途**和**風格**分開選：
- 用途（拍什麼、按什麼結構講）看 `references/formats.md`，只讀對應的那一節。
- 風格（長什麼樣、怎麼動、什麼聲音）先看 `references/styles/INDEX.md`，再**只讀選中的 1–2 個風格檔案**。風格可以直接用、改造（替換其中一兩條規則）、混搭（一主一輔，或者按段落切換媒介），也可以按 `styles/_template.md` 自訂。風格規則保持不變，故事、鏡頭和結構從使用者的主題來，不要沿用別的片子。每個風格檔案都有「辨識訊號」和「最俗的版本」兩節：按主題挑 2–3 個訊號（至少一個不在俗套裡），在 brief 裡寫明翻掉了俗套的哪幾條，或者為什麼保留。使用者選了風格，要的是一眼認出這個風格，兩三個訊號就夠了。
- 再按需翻 `references/craft.md`（手法庫）。

按 `references/brief-template.md` 寫 brief，核心是：

```yaml
Reel Read:
  format: [用途，formats.md 裡的類型]
  benchmark: [對標作品 · 學什麼 · 不學什麼]
  structure: [三個候選結構 → 選中哪個、為什麼]
  style: [styles/ 裡的風格（含改造點），或者混搭方案，或者自訂規則]
  signals: [挑了哪 2–3 個辨識訊號、為什麼；翻掉了俗套的哪幾條]
  takeaway: [觀眾記住的一句話或一個畫面]
  hook: [前 1 秒發生什麼]
  signature: [記憶點：第幾秒、什麼手法]
  palette / type / motion / camera / texture: [按所選風格寫出具體值]
  sound: [無聲 / 合成（聲音對標、律動、和聲、配器、曲線，見 sound.md 第 2 節）/ 使用者曲子（BPM、drop）]
  audio-sources: [BGM 與音效各自為 AI / 使用者 / 關閉]
  narration: [無 / 使用者原稿 TTS / 使用者錄音；有口播時句段時間軸路徑、人聲優先]
  forbidden: [這支片子的禁止清單]
```

接著寫分鏡表：無口播時保留**節拍網格 + 分鏡表**。有口播時把句段關聯到鏡頭與事件，寫明 `鏡頭 / 句段 ID | 要解釋的變化 | 物件起止狀態 | 繼承的物件與空間 | 關鍵事件及時間依據 | 鏡頭與聲音`。一鏡可以覆蓋多句，一句可以有多個動作；不把口播分句當作切鏡指令，也不要求逐句把原稿寫滿屏。實際區間在音訊準備後回填，不把字數估時當成最終對齊依據。長片另寫章節表、各章時長和跨章一致性規則。

使用者只說了一句「全力以赴」，也要把它翻譯成上面這份具體約束，否則結果就是抽卡。

### 第 3 步：風格幀（第二次停下來等使用者）

建專案：`sh <skill>/scripts/scaffold.sh <slug> [--audio synth|tone|layer|file|none]`（synth = 第 1 檔合成；只複製選中的那份 score，`file` 使用已準備好的最終音軌）。腳手架的引擎預設值只用於技術初始化，不能代替需求確認。starter 只用來驗證管線能跑通，畫面和文案都要換掉。

**A. 使用者已經定了風格**（或者給了明確的參考）：
以下指令中的秒數只是示例，實際取本片開場、記憶點與結尾的有效時間；短片和長片都不要照抄 14.5 秒。
1. 用真程式碼搭出 hook 幀、記憶點幀、結尾幀，配色、字型、文案都用最終的。
2. `render.mjs <slug> --still 0.6,7.2,14.5 --sheet`，自己先看一遍，明顯的問題修完再給使用者。依賴運動的方向，在工作區中展示本節要求的連續片段，不先編碼成 MP4。
3. 把 Reel Read 摘要、分鏡概要、風格幀發給使用者，問「方向對嗎？」。

**B. 使用者沒定風格（包括放手模式）**：給 **3 個拉開差距的方向**，規則見 `styles/INDEX.md`：
- A 貼合主題／品牌，B 換一種畫面語言（來自另一個分組），C 大膽（自訂、混搭或結構上很大膽，至少一個方向不是庫裡現成的）。
- 每個方向寫一段迷你 Reel Read（風格、對標、記憶點、配樂方向，3–5 行），並用真程式碼渲**一張**最能代表它的關鍵幀。三個方向的頁面放在同一個專案裡，用 `?dir=a|b|c` 切換。B、C 只為這一張關鍵幀服務，不必做成能播的整片。
- `render.mjs <slug> --directions a,b,c --at 14.5,2,0` 一次渲出三張並拼成帶標籤的 `qa/directions.png`，發給使用者，問「選哪個，或者怎麼混合？」。

兩種情況都**真的等使用者回覆**，再進入製作。TTS 專案同時附使用者原稿的分段方案和音色短樣（只使用使用者給的文字），一起確認聲音方向，不額外增設必停節點。使用者事先明確說過不用確認的，就自己選一個、寫明理由，自查後繼續；交付時把沒選的方向一起給使用者（B 情況附上 `qa/directions.png`，A 情況各寫一句另外兩個可能的方向），讓使用者回來還能換。

對依賴連續動作的方向，靜幀之外在工作區中展示 6–10 秒代表性運動片段（短於 6 秒的片子用全片），用播放頭和循環試聽選區定位，覆蓋一次狀態變化及前後承接；先自行看連續幀排除跳變。片段隨風格幀一起確認，無需提前匯出樣片。口播尚未生成時明確標為動作預演，不能聲稱已與語音精確對齊。風格確認與最終預覽確認分別確認方向和成片內容。

### 第 4 步：製作

製作前先讀 `references/stack.md`（頁面契約、確定性、各技術的坑）。要現成寫法時查 `references/recipes.md`。

**有口播時先鎖定口播時間軸**：按 `references/narration.md` 合成使用者原稿或匯入使用者錄音，取得真實時長和句段時間戳，再安排畫面。使用者錄音需透過可用轉錄工具或使用者提供的 SRT/JSON 獲得文本與時間；沒有可靠時間戳時不能聲稱已完成逐句對齊。發現時長衝突先確認，不靜默填充、裁切或變速。將真實區間匯入鏡頭表，保留口播停頓和重點，不強行對齊音樂小節。超過 2 分鐘按 `references/long-form.md` 分章製作，保留章節快取。

句段只提供同步範圍，鏡頭和主體運動可以連續跨句。關鍵變化需要詞級同步時，用真實詞時間或人工標註錨點，透過 `narration.js` 查詢，讓畫面與音效引用同一事件；只有句級時間時維持句級同步，不偽造逐字時點。製作過程中預設用 `editor.mjs` 帶聲音預覽、拖動與逐幀檢查；`preview.mjs` 保留為輕量除錯工具。預覽只驅動同一個 `render(t)`，不進入正式渲染。

1. 時間點全部寫進 `timeline.js`，頁面和 `score.mjs` 都從這裡 import。鏡頭表寫進 `SHOTS`（驗收時按鏡頭報運動），刻意的停留寫進 `HOLDS`（比如落版 `[[b(36), DUR]]`），要留呼吸的重拍寫進 `DROPS`，驗收工具會讀它們。轉場要對拍時，用 `revealOn(拍點, 轉場時長, 揭開點)` 倒推起點，讓新畫面露出來的那一幀落在拍上。
2. 逐個鏡頭做。使用者要看製作過程時，每鏡自查通過即發布該鏡頭的獨立可播放成果（`progress.mjs --stage scenes --shot <id> --total <鏡頭總數> --publish <該鏡預覽目錄>`），然後再做下一鏡；不把所有鏡頭寫完後一次補成 3/3，也不等全片素材齊全才給第一個預覽。每個鏡頭渲開頭、中段、結尾 3 張靜幀；關鍵狀態變化和鏡頭接縫另看連續小樣，檢查主體是否憑空重置、動作速度是否突變、鏡頭是否中斷。靜幀好看不能替代運動檢查，快速動作用 `inspect.mjs strip` 看連續幀。
3. 跑確定性檢查 `render.mjs <slug> --determinism`，不通過就先修。
4. 用網頁預覽檢查節奏與連續動作，不預設渲染低清代理或 MP4 小樣；靜幀和確定性檢查照常進行。確實需要離線片段時說明原因，在使用者同意後只渲必要範圍。
5. 按 brief 配好 `FPS`、`SIZE`、`AUDIO`、`LOOP`，完成下方聲音準備後進入第 6 步。此時不執行 `build.sh`、影片模式的 `render.mjs` 或 `build-long.mjs`。

**硬規則**：
- 畫面只由 t 決定：不用 `Math.random`、`Date.now`、rAF、定時器、CSS 動畫，幀和幀之間不儲存狀態。
- 字型和素材全部載入完，再設定 `READY = true`；字型放進專案自託管。
- 佈局從 `stageSize()` 返回的寬高推導，不寫死像素。

使用子幀運動模糊且有文案硬切時，可按 `references/stack.md` 的可選取樣上下文區分文案狀態與連續運動；匯出後檢查切換點的連續幀，避免子幀平均造成一幀文字疊印。

啟用製作進度時：風格幀與口播短樣自查後發布為圖片／音訊成果；鏡頭和混音形成可播放階段後，用 `progress.mjs --publish` 發布穩定副本。開工前更新 `running`，完成後把成果掛在對應階段：需求／腳本可發布 Markdown，風格幀發布圖片，聲音發布音訊，逐鏡頭發布可播放版本。等待使用者選擇用 `waiting`；未完成部分寫清楚，數量由成功發布的鏡頭計算。階段預覽不增加確認節點，不觸發 MP4 合成。最終短片用 `review --final` 在同一進度頁進入可調音、可匯出的工作區；長片仍逐章展示，確認全片後按原流程構建。

### 第 5 步：BGM、音效與混音

看 `references/sound.md`。BGM 和音效分別按確認的來源製作，允許使用者配樂 + AI 音效等組合。下表是 AI 合成的引擎選擇，不能用引擎預設值覆蓋已確認的素材來源。聲音方向（對標、律動、和聲、配器、曲線）在 brief 裡就定好：

| 檔 | 用什麼 | 適合 |
|---|---|---|
| 第 1 檔 · 內建合成 | `score.mjs`，Node 裡的合成器（鼓、手鼓、貝斯、鋪底、撥弦、馬林巴／鋼片／卡林巴、風琴、人聲鋪底、FM、環境底噪、音效、側鏈、混響、lo-fi 處理），零依賴 | 電子、UI、晶片音樂、氛圍、lo-fi、手作與玩具、大多數動效片 |
| 第 2 檔 · Tone.js | `score.tone.js`，在無頭瀏覽器裡用 Tone.js 離線渲染：取樣樂器（`audio.mjs samples salamander` 下載 CC BY 鋼琴）、卷積混響、更豐富的合成器和效果 | 需要真實樂器、空間感、電影感的風格 |
| 外部曲子 | 使用者提供的音樂（自己的、授權的、AI 音樂服務生成的） | 使用者已有配樂 |

- 構建：`audio.mjs build <slug>/score.mjs` 或 `score.tone.js`，都會輸出 −14 LUFS 的 `audio/music.wav`。
- 使用者曲子：無口播時先跑 `audio.mjs beats`（有 librosa 時自動使用）對齊 timeline，再在 score 裡 `S.load()` 疊音效。有口播時只把音樂節拍作為參考，調整音樂和音效配合語音，不移動已確認的口播時間軸。
- 無聲：BGM、音效和口播均關閉時跳過；僅關閉 BGM 不代表整片無聲。
- 有口播：音樂減少主旋律、密集打擊和大動態；音效只保留有資訊作用的動作，避開關鍵詞與句首。保留獨立軌，透過 `narration.mjs mix` 做人聲期間的避讓、統一響度和峰值處理。用真實句段時間戳核對畫面，聽感仍需使用者終審。

每次 build 之後都要對最終混音跑 `audio.mjs check`，看數值和圖；宿主支援試聽時再聽，不能把數值通過寫成「聽感已確認」。`timeline.js` 裡寫了 `DROPS` 時，它還會量出重拍前的凹陷和抬升，沒有呼吸就給 WARN。

### 第 6 步：工作區預覽（預設入口，等使用者確認匯出）

每次製作都讀 `references/editor.md`。已啟用製作進度的短片，在同一進度頁發布 `review --final` 作為最終工作區，沿用已確認的規格和匯出品質引數，無需另開入口；其餘情況執行 `node <skill>/scripts/editor.mjs <slug> --size <本片尺寸> --fps <本片幀率>`，並主動開啟列印的網址；宿主不能開啟瀏覽器時提供可存取的本機連結，等待使用者預覽回饋。無聲、無口播、短片、循環片也走這一步，不需要使用者再次提出「開啟工作區」。長片按 `long-form.md` 逐章開啟工作區預覽，第一版不假稱有跨頁面整片時間軸。

先自行檢查畫面、音軌、時長和錯誤，再交給使用者播放、拖動和調音。未編輯時直接使用原混音；音軌調整後更新試聽，確認目前混音已經載入。使用者提出修改就改完後重新整理、複看，不因上一版通過而自動匯出修改版。只有使用者點選「匯出影片」或明確確認目前預覽通過、可以匯出，才進入下一步；兩者都是匯出確認，無需再重複詢問。

把預覽連結、回饋、確認匯出的版本及音軌編輯記錄寫進 `brief.md` / `qa/review_log.md`。如果服務或瀏覽器不可用，說明阻礙並提供網頁預覽替代方案，不擅自改成先生成 MP4。子幀混合、DPR 超取樣和 ffmpeg 顆粒仍屬於匯出設定，告知預覽尚未模擬的部分，不靜默降低成片品質。使用者明確要求不預覽、直接匯出時記錄其指示，保留下面的全部技術驗收。

### 第 7 步：匯出與驗收

預覽通過後，單頁面優先在剪輯工作區點選「匯出影片」，由現有渲染器和驗收工具輸出編輯版 MP4。工作區的音訊修改不會自動寫回 `build.sh`，有編輯時匯出必須使用已試聽的目前工作階段，不能繞回原混音。未使用工作區音訊編輯時，也可在使用者確認後執行 `sh <slug>/build.sh`；它會構建配樂、檢查確定性、渲染、生成文字審片材料，並按相同規格驗收。混合音軌沿用 `AUDIO=file AUDIO_FILE=audio/final.wav sh build.sh`，舊的 synth/tone/layer/none 方式仍可用。長片確認後用 `build-long.mjs` 持久分章構建，詳見 `references/long-form.md`。

`--subframes`、`--dpr`、`--grain` 按 brief 傳入，工作區出口和手動構建使用同一組已確認規格；這些引數會增加耗時，開渲前報告預計時間。循環片另帶 `--loop` 驗收。預覽確認不替代匯出後的技術檢查和成片複核。

**技術檢查**：由程式判定，失敗就不能交付。

```bash
node <skill>/scripts/inspect.mjs qa <slug>/out/final.mp4 --out <slug>/qa/final \
  --expect-size 1920x1080 --expect-fps 30 --expect-duration 16 --audio required   # 無聲片用 --audio none；循環片加 --loop
```

它檢查檔案能否解碼、尺寸、幀率、時長、幀數、音軌、黑幀、響度、真峰值，以及循環接縫（需要時）。只要有一項 FAIL，退出碼就是 1，必須修好。沒傳的規格項會列成 `NOT CHECKED`，這時不算驗收通過。`build.sh` 會自動帶上規格。渲染工具本身也會拒絕發布幀數不對的檔案。

**審片**：給人判斷用，不是程式判定。看抽幀圖、手機尺寸抽幀圖、凍結段（`HOLDS` 裡宣告過的會標成刻意停留，其餘要判斷是不是空拍）、切點、按鏡頭的運動和閃幀、文字框景的標記圖（`qa/text-*.png`）、音訊圖，按 `references/review.md` 的審片表逐項寫下觀察和最嚴重的 3 個問題，有數字和圖表的片子要核對內容與數字口徑。修完只重渲有問題的那一段，再出整片，過程記到 `qa/review_log.md`。宿主支援子代理時，再派一個沒參與製作的代理只看這些材料挑問題（review.md「獨立審片」）。

有口播時額外執行 `narration.mjs check`，核對句段時間覆蓋、音訊長度與確認規格；逐句審查原稿、畫面與語音是否一致，自動檢查不能代替聽感審片。長片逐章審片，並檢查拼接處的畫面、聲音和時間軸。

審片結論是給使用者的參考，**不能代替使用者自己看片**。不適用的項標「不適用」，比如無聲作品的音畫同步，不要硬給分數。

### 第 8 步：交付

告訴使用者：
- 實際成片路徑：工作區匯出為 `out/editor-<task-id>.mp4`，原構建為 `out/final.mp4`；同時給出 `out/poster.png`（poster：`render.mjs <slug> --poster <t>`）。
- `brief.md`：完整的結構化提示詞、需求與風格確認、最終預覽及匯出確認記錄，可以重用，不含 API 憑證。
- 有口播時附使用者原稿、句段時間軸和各軌來源；長片附章節 manifest 和斷點重建指令。
- 技術檢查結果（全部 PASS）、審片記錄裡還沒解決的問題、渲染用時。
- 怎麼重新開啟工作區、如何重建目前編輯版（見 editor.md），原構建仍可 `sh build.sh`，以及怎麼只改一段。
- 第三方素材（字型、使用者素材、曲子）的來源和授權；事實類內容提醒使用者再核對一遍。

複盤結論和複核證據儲存在專案的 `qa/review_log.md`，與本次製作檔案一起交付。

## 底線（所有風格都要守）

1. **需求與原稿**：必填資訊經確認；影片不超過 20 分鐘；TTS 原稿必須來自使用者。時長衝突須確認，不擅自改稿、截斷或變速。
2. **事實準確**：產品功能、數字、名稱只來自使用者或可靠來源，不確定的標出來。
3. **文字可讀**：字號在手機尺寸下看得清，停留時間夠讀完（見 craft.md 第 7 節）；文字不溢位、不重疊、不被遮擋。
4. **素材有授權**：logo、截圖、字型、曲子都要能用，並在交付時列出來。
5. **技術正確**：確定性渲染，技術檢查全部通過，沒有黑幀，結尾不能戛然而止（落版定格或無縫循環）。
6. **風格一致**：選定的風格規則從頭守到尾，不落入 brief 的禁止清單。

除此之外，鏡頭動多少、用不用彈簧、音效密度、節奏快慢，都按風格和內容來定（見 references/styles/ 和 craft.md）。
